# Frontier-15

Date: 2026-04-24

This report follows `frontier-14`.

`frontier-14` found the first genuinely positive branch in the repo:

- polyglot digest collapses the commitment and dummy-signature pools,
- same `n = 150`, all-signed `10 / 10` fits easily under the byte limit,
- and the byte/op frontier is materially better than the public QSB points.

That part still holds.

But the next step had to be stricter:

1. tighten the security accounting to match the upstream QSB paper,
2. price trusted setup as actual `HASH160` work and time,
3. and test whether a partial-polyglot family can keep most of the gain with
   less setup pain.

The new tool for this step is `tools/polyglot_setup_frontier.py`.

## Result 1: frontier-14 overstated second-preimage security

The main correction is simple and important.

`frontier-14` treated no-bonus polyglot second-preimage resistance as:

- pinning bits
- plus signed digest bits

That is too optimistic.

Under the upstream QSB paper’s own model, second-preimage cost is driven by:

- one pinning puzzle,
- plus one specific round puzzle for round 1,
- plus one specific round puzzle for round 2,

with reductions only from free bonus-key choice.

So for any no-bonus two-round construction that keeps the same
`~2^46.4` round puzzle, the corrected second-preimage level is still:

- `3 * 46.4 = 139.2` bits

not `146+` bits or `158+` bits.

That changes the interpretation of full polyglot:

- it **does** improve collision resistance and honest-subset abundance,
- it **does not** create a new second-preimage regime.

## Result 2: full polyglot is still real, but the win is collision plus bytes, not a security jackpot

The corrected same-`n` full-polyglot point is:

- `n = 150`
- rounds: `10 + 0b`, `10 + 0b`
- `6953` bytes
- `201` ops
- `100.11` signed digest bits
- `139.20` corrected second-preimage bits
- `96.45` collision bits

So the right reading is now:

- same-`n` full polyglot saves about `3000` script bytes,
- keeps the baseline no-bonus second-preimage level,
- and raises collision resistance from the public baseline `88.66` to `96.45`.

That is still a good result.

It is just narrower than `frontier-14` first suggested.

## Result 3: trusted setup is expensive enough to dominate the practical story

The corrected tool prices setup as:

- one valid polyglot element per trusted signed slot,
- each costing about `2^46.4` `HASH160` trials in expectation,
- for a total of `2^46.4 * elements`.

For the same-`n` full-polyglot point, that means:

- `300` trusted polyglot elements,
- `2^54.63` expected `HASH160` evaluations,
- about `322.4` days at `1 GH/s`,
- about `32.2` days at `10 GH/s`.

I also ran a crude local sanity check on this machine:

```text
python3 - <<'PY'
import hashlib, time
N = 1_000_000
msg = b'x' * 33
start = time.perf_counter()
for _ in range(N):
    hashlib.new('ripemd160', hashlib.sha256(msg).digest()).digest()
end = time.perf_counter()
print(f'hash160_per_sec={N / (end - start):.2f}')
PY
```

That measured about `0.86 MH/s` through the local Python/OpenSSL path.

That is not a serious upper bound on trusted hardware performance, but it is a
useful lower-bound sanity check:

- `192` elements would still be about `658` years there,
- `224` elements would still be about `768` years there,
- `300` elements would still be about `1029` years there.

So CPU-side trusted setup is dead.

The interesting regime is a **trusted local accelerator**, not a CPU script.

## Result 4: a split-pool partial-polyglot family is the first setup-aware variant worth keeping

The new tool studies one explicit partial family:

- signed selections come from a trusted polyglot pool of size `m`,
- bonus selections come from a separate dummy-signature pool of size `q`,
- bonus entries do **not** require HORS commitments or trusted grinding,
- and the same split-pool round is used in both digest rounds.

That matters for two reasons:

1. trusted setup now scales with `m`, not with every bonus entry;
2. bonus entries are in a separate pool, so they do **not** introduce the
   same collision penalty that current QSB bonus keys do.

### First point that beats Config A on both second-preimage and collision

- setup cap: `192` trusted elements total
- per round: `m = 96`, `q = 72`, `s = 9`, `b = 1`
- `6099` bytes
- `195` ops
- `80.48` signed digest bits
- `126.86` second-preimage bits
- `86.64` collision bits
- setup time: `206.3` days at `1 GH/s`, `20.6` days at `10 GH/s`

Compare this to public Config A:

- `118.74` second-preimage bits
- `78.24` collision bits

So the first clear setup-aware win over Config A does exist.

But it still needs a lot of trusted polyglot setup.

### First point that beats the public baseline on collision

- setup cap: `224` trusted elements total
- per round: `m = 112`, `q = 17`, `s = 9`, `b = 1`
- `5657` bytes
- `195` ops
- `84.64` signed digest bits
- `131.03` second-preimage bits
- `88.72` collision bits
- setup time: `240.7` days at `1 GH/s`, `24.1` days at `10 GH/s`

This is the first split-pool point that edges past the public baseline
collision level (`88.66`) while staying far below the script-size limit.

## Result 5: there is no low-setup miracle yet

The setup-aware frontier by symmetric setup cap is:

- cap `128`: `m = 64`, `q = 206`, `s = 8`, `b = 2`
  - `78.44` collision bits
  - `110.47` second-preimage bits
- cap `160`: `m = 80`, `q = 81`, `s = 8`, `b = 2`
  - `81.15` collision bits
  - `115.88` second-preimage bits
- cap `192`: `m = 96`, `q = 72`, `s = 9`, `b = 1`
  - `86.64` collision bits
  - `126.86` second-preimage bits
- cap `224`: `m = 112`, `q = 17`, `s = 9`, `b = 1`
  - `88.72` collision bits
  - `131.03` second-preimage bits
- cap `256`: `m = 128`, `q = 0`, `s = 10`, `b = 0`
  - `94.09` collision bits
  - `139.20` second-preimage bits
- cap `300`: `m = 150`, `q = 0`, `s = 10`, `b = 0`
  - `96.45` collision bits
  - `139.20` second-preimage bits

So the practical picture is sharper now:

- below about `192` trusted elements, the split-pool family does not clearly
  dominate the no-setup public points;
- around `192` to `224` trusted elements, it starts to become genuinely
  competitive;
- by `256+` trusted elements, the frontier largely collapses back toward
  no-bonus full polyglot.

## Result 6: what the repo should do next

This is now the highest-signal conclusion in the repo:

**polyglot is still the only positive branch after the DER work, but its real value is collision/script efficiency, not a free second-preimage jump.**

And the next serious questions are now narrower:

1. can the split-pool family be made more script-faithful than the current
   family model;
2. can setup be reduced below the `~192`-element threshold without collapsing
   back under Config A;
3. or does the real next frontier require a different trusted primitive rather
   than more local tuning of the QSB script surface.
