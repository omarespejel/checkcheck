# Frontier-8

Date: 2026-04-24

This report follows `frontier-7`.

After `frontier-7`, the DER story had reached an awkward point:

- exact `13` was the first overlap-bearing exact DER surface,
- but even that explicit overlap-bearing family still stayed subset-like.

So the next useful question was no longer "do overlaps exist?"

It was:

> do deletions ever create fresh later-match occurrences that were not present before?

That is the first mechanized explanation for why a family can have overlaps and still fail to generate extra `FindAndDelete` states.

The new tool for this step is `tools/fad_cascade_frontier.py`.

## Result 1: toy overlap has a real fresh-occurrence cascade

The best toy overlap family from `frontier-3` is:

- family: `01`, `02`, `0101`, `0201`
- script order: `02`, `0101`, `0201`, `01`

The new tool tracks byte provenance through each deletion and asks whether a deletion creates a fresh occurrence of another selectable token that was not present before.

For the toy family, it finds a real witness:

- selection order: `[0, 1]`
- after deleting token `1`, a fresh later-match occurrence of token `3` appears
- fresh occurrence provenance indices: `[3, 9]`

That is the missing mechanized bridge from "order matters" to "why order matters."

Toy overlap is not just overlap-bearing. It is **cascade-bearing**.

## Result 2: exact-13 overlap-bearing DER families are cascade-free

`frontier-7` built an explicit exact-`13` valid DER pool whose pushed tokens have real pairwise overlap.

The new tool now checks whether those overlap-bearing families ever produce fresh later-match occurrences.

### Exact-13 overlap pool, ordered `2`-of-`4`

- pool size: `6`
- family size: `4`
- selection size: `2`
- exhaustive search over all `C(6,4) * 4! = 360` script orders
- result: `cascade_found: false`

### Exact-13 overlap pool, ordered `3`-of-`5`

- pool size: `6`
- family size: `5`
- selection size: `3`
- exhaustive search over all `C(6,5) * 5! = 720` script orders
- result: `cascade_found: false`

So exact-13 overlap-bearing DER is not just subset-like in outcome space.

It is cascade-free in the stronger operational sense:

**deleting one valid token never creates a fresh later-match occurrence of another valid token in the searched exact-13 overlap pool.**

That explains why overlap existence still failed to produce extra states.

## Result 3: random exact DER families also showed no cascade witnesses

The tool then runs random cascade search over exact DER surfaces.

Searched regimes:

- exact `13`, `m=4`, `t=2`, `2000` trials
- exact `14`, `m=4`, `t=2`, `2000` trials
- exact `15`, `m=4`, `t=2`, `1500` trials
- exact `13`, `m=5`, `t=3`, `1000` trials

Result in every case:

- `cascade_found: false`

That does not prove the full DER space is cascade-free.

But it is exactly the kind of evidence the repo needed:

- toy overlap: cascade exists
- explicit overlap-bearing DER: no cascade
- random exact DER: no cascade found

So the repo now has a plausible explanation for the negative results from `frontier-4` through `frontier-7`.

## Result 4: overlap is necessary but not sufficient

This is the main takeaway.

The repo has now separated three different notions:

1. plain subset behavior,
2. overlap-bearing token families,
3. cascade-bearing token families.

The data now suggests:

- extra `FindAndDelete` expressivity needs more than overlap,
- it needs a deletion to create a fresh later-match occurrence,
- and the DER-shaped families explored so far do not seem to have that property.

That is stronger than the prior negative result.

Before this step, the repo only knew:

"even overlap-bearing DER still looks subset-like."

Now it knows:

"even overlap-bearing DER appears cascade-free, which explains why it stays subset-like."

## What is left

The next worthwhile moves are now narrower and more informed:

1. search for valid selectable blob families that are explicitly **cascade-bearing**, not merely overlap-bearing;
2. formalize a proposition that cascade-freedom implies order-independence for these `FindAndDelete` families;
3. if no plausible valid cascade-bearing family exists, stop spending cycles on deletion overlap and move to a different verification surface.

That is where the repo should go next.
