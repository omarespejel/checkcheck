# Frontier-12

Date: 2026-04-24

This report follows `frontier-11`.

`frontier-11` showed that the first direct valid-DER lift of the toy
destructive-conflict gadget already fails.

That left the next concrete DER question:

> what if the payload explicitly plants the pushed-token anchor twice?

The new tool for this step is `tools/der_double_anchor_frontier.py`.

It studies **double-anchor DER** families:

- exact-length DER payloads,
- one-byte `r`,
- `s` begins with the exact pushed-token anchor for that same length,
- and then embeds that same anchor one more time inside the body.

This is the first checked-in DER family in the repo that explicitly tries to
manufacture multiple pre-existing anchor instances inside a valid token, rather
than just one.

## Result 3: this is the strongest DER exhaustion point so far

The DER story is now much tighter than it was before:

- overlap-bearing exact-`13` DER exists, but stays conflict-free and subset-like;
- the single-anchor conflict-gadget lift fails;
- and now even double-anchor DER templates stay conflict-free and subset-like.

That matters because the negative result is no longer “random DER did not show
anything.”

It is now:

**the repo has tried increasingly mechanism-aware valid-DER constructions, and they still collapse to plain subset behavior.**

## Result 4: what the repo should do next

The next meaningful branch is no longer “one more short DER motif.”

The realistic options are now:

1. **repeated-body or multi-anchor-plus-body DER**
   use three or more planted internal structures, not just two anchors;
2. **different valid selectable blob family**
   stop insisting on this DER shape and test a different class of valid pushed
   blobs entirely;
3. **leave valid-blob `FindAndDelete` search behind**
   if these stronger constructions also fail, move the repo to a different
   verification surface.

At this point, plain DER-shaped selectable blobs look close to exhausted.
