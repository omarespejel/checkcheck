# Frontier-16

Date: 2026-04-24

This report follows `frontier-15`.

`frontier-15` made the polyglot branch stricter:

- corrected the second-preimage accounting,
- priced trusted setup explicitly,
- and found a symmetric split-pool family that first beats Config A around
  `192` trusted elements and first beats the public baseline collision level
  around `224`.

That immediately raised the next question:

> is that `192`-element floor real, or is it just an artifact of forcing the
> two digest rounds to be symmetric?

The updated tool for this step is still `tools/polyglot_setup_frontier.py`,
but it now does two new things:

1. adds explicit witness-size accounting;
2. searches **asymmetric** split-pool rounds, with different trusted pool sizes
   and bonus-pool sizes in round 1 and round 2.

## Result 1: witness size is not the blocker

The first useful negative result is that witness growth stays tame across the
interesting polyglot points.

### Corrected full polyglot (`150`, `10 / 10`)

- script bytes: `6953`
- witness bytes: `1364`

### Best symmetric split-pool point at `192` trusted elements

- script bytes: `6099`
- witness bytes: `1302`

### First asymmetric point beating Config A

- script bytes: `6358`
- witness bytes: `1348`

### Strong asymmetric point at `224` trusted elements

- script bytes: `5593`
- witness bytes: `1323`

So the new search says something clean:

**witness size is roughly flat across the interesting region (`~1300`--`1360` bytes). The real constraint is still trusted setup, not witness blowup.**

## Result 2: asymmetry lowers the first Config-A-beating threshold from `192` to `143`

This is the main positive result of the step.

The first asymmetric split-pool point that beats Config A on both
second-preimage and collision appears at:

- total trusted elements: `143`
- round 1: `m = 64`, `q = 206`, `s = 8`, `b = 2`
- round 2: `m = 79`, `q = 65`, `s = 10`, `b = 1`
- `6358` script bytes
- `201` ops
- `1348` witness bytes
- `72.43` signed digest bits
- `118.81` second-preimage bits
- `82.62` collision bits

Compare that to the symmetric threshold from `frontier-15`:

- `192` trusted elements
- `6099` bytes
- `126.86` second-preimage bits
- `86.64` collision bits

So asymmetry does something real:

- it lowers the **threshold crossing** by `49` trusted elements,
- even though the threshold point itself is only a narrow win on
  second-preimage (`118.81` vs. Config A `118.74`).

That is exactly the kind of result we wanted from this step:

**the `192`-element floor was not fundamental. It was partly a symmetry artifact.**

## Result 3: the first baseline-collision crossing moves from `224` to `200`

The asymmetric search also lowers the first point that edges past the public
baseline collision level:

- total trusted elements: `200`
- round 1: `m = 82`, `q = 317`, `s = 9`, `b = 1`
- round 2: `m = 118`, `q = 0`, `s = 10`, `b = 0`
- `7971` script bytes
- `198` ops
- `1333` witness bytes
- `84.56` signed digest bits
- `130.89` second-preimage bits
- `88.68` collision bits

The old symmetric threshold was:

- `224` trusted elements
- `5657` bytes
- `131.03` second-preimage bits
- `88.72` collision bits

So asymmetry again lowers the threshold, but only slightly:

- `224` down to `200` trusted elements

The important nuance is that the first crossing is numerically very narrow
(`88.68` vs. baseline `88.66`), so the stronger practical point is still a bit
higher on the curve.

## Result 4: the stronger asymmetric point is at `224`, not `200`

The best asymmetric point at the old `224` trusted-element cap is much better
than the first crossing:

- round 1: `m = 106`, `q = 29`, `s = 9`, `b = 1`
- round 2: `m = 118`, `q = 0`, `s = 10`, `b = 0`
- `5593` script bytes
- `198` ops
- `1323` witness bytes
- `88.05` signed digest bits
- `134.34` second-preimage bits
- `90.42` collision bits

This is a better point than the symmetric `224` result in every important
dimension:

- fewer script bytes (`5593` vs. `5657`)
- still well below the opcode limit (`198` vs. `195`)
- much stronger collision (`90.42` vs. `88.72`)
- stronger second-preimage (`134.34` vs. `131.03`)

So the practical reading is:

- asymmetry lowers the first thresholds,
- and at the same setup cap it also finds better points.

## Result 5: the asymmetric curve now looks more plausible, but setup is still the bottleneck

The best asymmetric points by setup cap are:

- cap `128`
  - `81.09` collision bits
  - `115.76` second-preimage bits
- cap `160`
  - `84.16` collision bits
  - `121.85` second-preimage bits
- cap `192`
  - `86.64` collision bits
  - `126.68` second-preimage bits
- cap `224`
  - `90.42` collision bits
  - `134.34` second-preimage bits
- cap `256`
  - collapses back to no-bonus full polyglot
- cap `300`
  - same full-polyglot endpoint as before

So the new picture is sharper again:

- asymmetry makes the setup threshold meaningfully lower;
- the best curve is now clearly **asymmetric**, not symmetric;
- but setup is still the binding cost.

The branch did not suddenly become cheap.

It just became less bad than the symmetric analysis suggested.

## Result 6: what the repo should do next

This is the strongest conclusion after `frontier-16`:

**the right partial-polyglot family is asymmetric, and the setup floor is lower than `frontier-15` suggested, but trusted setup is still the dominant bottleneck.**

So the next serious steps should be:

1. make the asymmetric split-pool family more script-faithful:
   explicit stack layout, exact round semantics, and concrete script builder
   logic;
2. test whether the `143`-element threshold survives once the current family
   model is turned into a more executable script description;
3. try to reduce the threshold further without losing the asymmetry gain.
