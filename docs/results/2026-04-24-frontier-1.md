# Frontier-1

Date: 2026-04-24

This report supersedes the earlier grouped-choice optimism in `frontier-0`.

## Calibration target

Imported upstream baseline:

- repo: `avihu28/Quantum-Safe-Bitcoin-Transactions`
- pinned commit: `861960e4f67d19ddeadb68cc9359a3257f461dde`

The imported builder was used directly to measure script sizes for the public configurations.

## Result 1: QSB is already byte-saturated

Measured with `python3 tools/frontier_model.py`:

| Config | Full script bytes | Ops | Signed digest bits |
|---|---:|---:|---:|
| Baseline `8,8` | `9953` | `197` | `84.51` |
| Config A `8+1b,7+2b` | `9967` | `201` | `80.35` |
| Alt `8+1b,8` | `9966` | `202` | `84.51` |

The key point is not just that the scripts are near the limit. It is how the bytes are spent.

For `n = 150` and two rounds:

- commitments: `2 * 150 * 21 = 6300` bytes
- dummy signatures: `2 * 150 * 10 = 3000` bytes
- total static choice bytes: `9300`

So `9300 / 10000 = 93%` of the entire script budget is already consumed by hardcoded choice material.

That means any competing design that needs materially more hardcoded choices is almost dead on arrival.

## Result 2: grouped-choice is combinatorially dominated under the same reveal budget

Compare one HORS-style round to a grouped-choice round.

For the public baseline round:

- total hardcoded options: `150`
- signed reveals: `8`
- HORS entropy: `log2 C(150, 8) = 42.26` bits

For grouped-choice with the same `150` hardcoded options and the same `8` reveals, the best case is equal-sized groups:

- maximum grouped-choice entropy: `8 * log2(150 / 8) = 33.83` bits

That is an `8.43` bit deficit in a single round.

To match the same `42.26` bits with only `8` reveals, grouped-choice needs:

- `312` hardcoded options
- `312 * 31 = 9672` static bytes

That is only for one round’s choices, before the rest of the script.

This is the first real pivot in the project:

**plain grouped-choice does not beat HORS-like subset encoding under today’s Bitcoin limits.**

## Result 3: even the optimistic grouped-choice frontier loses badly

The model then searched for the best grouped-choice point under QSB-like constraints:

- script limit: `10,000` bytes
- op limit: `201`
- optimistic per-round byte accounting calibrated from the all-signed upstream baseline
- optimistic round op accounting reused from the upstream script structure

Best point found:

- round 1: `5` reveals over `94` options
- round 2: `11` reveals over `207` options
- total: `9983` bytes, `197` ops
- raw digest bits: `67.74`

That still loses badly to the public QSB points:

- `67.74` vs `80.35` signed digest bits for Config A
- `67.74` vs `84.51` signed digest bits for the baseline

This is important because the grouped-choice model is already optimistic. If the optimistic frontier still loses, the real construction is even less attractive.

## Result 4: tree-style modern signatures are blocked by Script expressivity, not by abstract cryptography

A tree-based limited-use signature family would normally try to store roots on chain and reveal authentication paths in the witness.

For a `~42` bit round with `8` selected leaves, an optimistic control gives:

- about `39` leaves per tree
- depth `6`
- only `160` root bytes on chain
- but at least `960` witness bytes of auth paths
- and `48` path-composition hash steps

That would be interesting in a world with a clean path-composition primitive.

But current Bitcoin Script does not expose that. Without `OP_CAT`-style composition, this family is not the right current-Bitcoin competitor.

So the blocker is sharper than “modern hashes are unavailable”:

**current Bitcoin is good at hardcoding many choices and selecting subsets, but bad at composing hash paths.**

That is why the old-looking HORS/subset approach is so competitive.

## Bottom line

The first strong result from this repo is negative:

1. grouped-choice is not the next frontier under current Bitcoin rules
2. naive tree-style modern ports are blocked by Script expressivity
3. the public QSB design looks much closer to the no-softfork frontier than the initial intuition suggested

## What this changes

The next thing worth exploring is not “another grouped-choice variant.”

It is one of these:

1. A construction that compresses many logical choices into one checked opening.
2. A way to get more entropy per reveal without increasing hardcoded option count.
3. A different verification surface entirely, rather than trying to out-HORS HORS with plain local choices.
