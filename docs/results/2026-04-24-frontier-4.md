# Frontier-4

Date: 2026-04-24

This report asks a narrower follow-up question after `frontier-3`.

The key open ambiguity was:

> Does overlap-coded `FindAndDelete` disappear because QSB uses fixed-length 9-byte tokens, or because the actual valid minimal-DER token surface is much more rigid than arbitrary bytes?

That distinction matters. If fixed length alone killed overlap, the overlap direction would be mostly dead. If arbitrary fixed-length payloads still overlap but valid minimal-DER ones do not, then the real blocker is the validity surface, not the length.

## Result 1: fixed length alone does not kill overlap

The updated tool `tools/fad_overlap_search.py` now does exact exhaustive search over several fixed-length families with `4` selectable payloads and ordered `2`-of-`4` witness deletion.

Results:

| Family | Best unique ordered outcomes | Plain subset baseline | Extra overlap states? |
|---|---:|---:|---|
| binary length `2` | `9` | `6` | yes |
| binary length `3` | `6` | `6` | no |
| binary length `4` | `6` | `6` | no |
| ternary length `2` | `9` | `6` | yes |
| ternary length `3` | `10` | `6` | yes |

So fixed length by itself is not the blocker.

Some fixed-length families collapse back to plain subset behavior, but others still realize real overlap gains.

That already sharpens the frontier:

**the failure of QSB’s current surface is not explained by "all fixed-length pushes are too rigid."**

## Result 2: engineered arbitrary `9`-byte payloads still overlap

The tool then runs a random search over arbitrary fixed-length `9`-byte payloads drawn from a small alphabet `{01, 02, 09}`.

Best family found in `50,000` trials:

- unique ordered outcomes: `8`
- plain subset baseline: `6`
- max outcomes for one unordered subset: `2`

Best payload family:

- `020101010109020909`
- `020909020902010101`
- `090202010109010902`
- `090209020101010902`

Best script order:

- `020909020902010101`
- `090202010109010902`
- `020101010109020909`
- `090209020101010902`

This is already enough to answer the construction question:

**even at the exact `9`-byte payload length, overlap-coded deletion is still achievable in principle.**

So byte length alone is not what kills the idea.

## Result 3: the valid minimal-DER surface is cross-bifix-free

The valid QSB dummy-signature surface is much narrower.

Each pushed token has the exact form:

`09 30 06 02 01 <r> 02 01 <s> 03`

with:

- `r` restricted to valid small secp256k1 x-coordinates in `[1, 127]`
- `s` in `[1, 127]`

That gives a total valid surface size of:

- `58` valid `r` values
- `127` valid `s` values
- `58 * 127 = 7366` valid minimal `9`-byte signatures

The updated tool checks the full surface for distinct proper prefix/suffix overlaps between pushed tokens.

Result:

- surface size: `7366`
- token size: `10` bytes including the push opcode
- `cross_bifix_free: true`
- maximum distinct proper overlap: `0`

This is stronger than a random non-hit. It means no valid pushed token has a proper suffix equal to a proper prefix of any other valid pushed token on this surface.

There is also a direct byte-structure reason:

1. Any valid pushed token starts with `09 30 06 02 01`.
2. A proper overlap would have to start at an internal `09`.
3. Inside a valid minimal token, the only internal `09` positions are when `r = 09` or `s = 09`.
4. If the overlap starts at the `r` byte, the next byte is `02`, not the required prefix byte `30`.
5. If the overlap starts at the `s` byte, the next byte is `03`, not `30`.

So no proper overlap can even begin.

That gives the first genuinely structural negative result in this repo:

**the minimal valid DER surface used by QSB is cross-bifix-free, so overlap-coded `FindAndDelete` cannot arise there.**

## Result 4: random search over valid minimal-DER families agrees with the structural result

The tool also runs a random search over actual valid minimal `9`-byte DER signatures.

In `200,000` random `4`-token families:

- best unique ordered outcomes: `6`
- plain subset baseline: `6`
- best unordered-subset multiplicity: `1`

So the random search agrees with the structural argument: the valid minimal-DER surface shows no overlap gain.

## Result 5: this closes the "engineered overlap inside current minimal DER" path

This changes the frontier again.

Before this run, the remaining hope was:

> maybe the current QSB token family simply has not been engineered hard enough.

After this run, that hope is much weaker.

The stronger statement now is:

- arbitrary bytes can realize overlap
- fixed `9`-byte payloads can realize overlap
- but current valid minimal-DER QSB tokens cannot, because the surface is cross-bifix-free

So the next interesting directions are no longer:

- tweak ordering
- search harder over current minimal `9`-byte signatures
- try another small overlap heuristic on the same surface

Those are basically exhausted.

## What is left

If there is another overlap-style frontier left, it likely has to come from one of these:

1. Longer or non-minimal but still valid signature-shaped selectable blobs.
2. A different valid selectable blob family entirely, not the current minimal-DER dummy-signature surface.
3. A construction that buys more searched states per static byte without relying on suffix/prefix overlap in the minimal token family.

That is a better next step than spending another cycle on minimal `9`-byte DER.
