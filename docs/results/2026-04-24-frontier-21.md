# Frontier-21

Date: 2026-04-24

This report follows `frontier-20`.

`frontier-20` said the next gate should be an external interpreter gate. That
gate found a real issue.

## Result 1: the previous op accounting was missing CHECKMULTISIG key charges

`python-bitcoinlib` rejected the old `strong_practical_224` point with:

```text
MaxOpCountError: EvalScript: max opcode count exceeded
```

Root cause:

- the repo was counting each `OP_CHECKMULTISIG` as one non-push opcode;
- Bitcoin's script evaluator also adds the number of public keys to the opcode
  counter for `OP_CHECKMULTISIG`;
- so an 11-of-11 `CHECKMULTISIG` costs `12` counted ops, not `1`.

That invalidates the old `143`, `198`, and `224` frontier-20 points under real
`MAX_OPS_PER_SCRIPT` accounting.

This is the right kind of failure. It came from a real interpreter, not another
spreadsheet model.

## Result 3: concrete byte-level interpreter gate passes for the corrected baseline crossing

New tool:

```text
python3 tools/polyglot_interpreter_gate.py
```

This tool emits concrete script bytes and scriptSig bytes for
`baseline_collision_sigop_corrected_258`, with actual `HASH160(preimage) ==
commitment` consistency for every HORS commitment. Then it runs those bytes
through `python-bitcoinlib==0.12.2`.

Interpretation:

- script parsing works;
- actual push encodings work;
- actual `OP_HASH160` / `OP_EQUALVERIFY` checks work;
- actual stack movement works in an independent interpreter;
- cleanstack still fails, as expected;
- real crypto still fails, as expected, because we have not generated valid
  transaction-bound ECDSA signatures or solved the hash-to-signature puzzle.

## Go/no-go

Decision:

**GO for one more concrete implementation gate.**

But the claim is weaker than before:

- the cheap polyglot gadget is real at the byte/interpreter level;
- the old improvement numbers were too optimistic because of sigop accounting;
- the corrected baseline-collision crossing is much closer to the edge:
  `9131` bytes and `197 / 201` counted ops;
- cleanstack remains impossible without a different design;
- full cryptographic regtest remains unproven.

## Next gate

The next gate should be narrow:

1. build a trusted-setup artifact generator for
   `baseline_collision_sigop_corrected_258`;
2. replace the signature stubs with actual transaction-bound signatures and
   recovered public keys;
3. rerun the same interpreter gate without stubs;
4. stop if the setup search cannot generate the needed polyglot
   commitment/signature values within a realistic budget.

No more frontier tuning should happen until that cryptographic setup gate is
clear.

## Bottom line

The branch survived the external interpreter gate, but only after losing a big
chunk of the earlier claimed advantage.

The interesting result is now:

**a corrected, byte-level, externally interpreted polyglot candidate crosses the
baseline collision level at `258` trusted elements under non-cleanstack,
signature-stubbed consensus semantics.**

That is still worth one more implementation step, but it is no longer a clean
`143`-element story.
