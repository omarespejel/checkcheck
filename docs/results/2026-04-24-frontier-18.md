# Frontier-18

Date: 2026-04-24

This report follows `frontier-17`.

`frontier-17` gave a no-go on the old asymmetric partial-polyglot model because
the stack constants were not executable under the documented witness layout.

This step asks the next question:

> if we make the round stack-correct, does the asymmetric polyglot result
> survive?

The new tool is:

```text
python3 tools/stack_correct_polyglot_frontier.py --signed-gadget copy_roll
```

## What changed

The new tool builds and symbolically executes a conservative stack-correct
split-pool round.

For signed polyglot selections it uses this safer shape:

1. roll the witness index;
2. sanitize it;
3. use `OP_PICK` to copy the selected hardcoded polyglot element for the
   `HASH160(preimage) == element` check;
4. use `OP_ROLL` to move the same hardcoded element into the
   `CHECKMULTISIG` signature zone.

For bonus selections it rolls directly from the separate dummy-signature pool.

For the `CHECKMULTISIG` tail it uses `OP_SWAP` to place `key_nonce` above the
signature count. This avoids the `OP_2 OP_ROLL` stack movement that failed in
`frontier-17`.

This is still not a full regtest transaction builder. It validates the round
script layer:

- concrete script bytes;
- non-push opcode count;
- selected hardcoded elements;
- preimage equality checks;
- puzzle key movement;
- `CHECKMULTISIG` stack shape.

- round script bytes: `3715`

```text
alternate_index_validation=pass
alternate_selected_poly=P63,P62,P61,P60,P59,P58,P57,P56
alternate_selected_bonus=B205,B204
```

So we now have an actual stack-correct selection skeleton.

That is the positive result.

## Result 2: the old `143` trusted-element result does not survive

The cost of making the polyglot selection stack-correct is material.

The old model assumed a cheaper signed-selection path. The conservative
stack-correct path needs to both:

- copy the selected hardcoded element for equality checking;
- and move the hardcoded element into the signature zone for `CHECKMULTISIG`.

That extra stack work pushes the old `143` point over budget.

The first stack-correct point that beats Config A is now:

- setup total: `293`
- round 1: `m = 98`, `q = 203`, `s = 5`, `b = 3`
- round 2: `m = 195`, `q = 0`, `s = 10`, `b = 0`
- script bytes: `8852`
- ops: `199`
- witness bytes: `1185`
- signed digest bits: `79.96`
- second-preimage bits: `118.81`
- collision bits: `86.38`
- setup time: `314.9d@1GH/s`, `31.5d@10GH/s`

That is a very different result from `frontier-16`.

`frontier-16` said:

- first Config-A crossing at `143` trusted elements.

`frontier-18` says:

- first stack-correct Config-A crossing at `293` trusted elements.

So the `143` result was a model artifact.

## Result 4: go/no-go decision

Decision:

**NO-GO on the current asymmetric partial-polyglot path as the next frontier.**

The reason is now stronger than `frontier-17`:

- `frontier-17` showed the old model was not script-faithful.
- `frontier-18` shows a conservative stack-correct version exists, but the
  advantage mostly disappears.

The only way to reopen this branch is to find a lower-op signed-selection
gadget that is also stack-correct.

That is now a narrow research problem:

> can a polyglot HORS selection both verify `HASH160(preimage)` and feed the
> selected signature into `CHECKMULTISIG` with fewer stack ops than the
> conservative `OP_PICK + OP_ROLL` skeleton?

If yes, the old asymmetric frontier may come back.

If no, this branch should stop.

## Bottom line

The repo now has the answer we needed:

**The asymmetric polyglot idea is not dead mathematically, but it is not the
best next engineering bet under the current stack-correct skeleton.**

The next worthwhile move is not more optimizer search.

It is either:

1. find a strictly cheaper stack-correct polyglot selection gadget; or
2. pivot to another QSB follow-up path.
