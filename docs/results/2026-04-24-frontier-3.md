# Frontier-3

Date: 2026-04-24

This report asks whether there is still an unexplored verification surface hiding inside `FindAndDelete` itself.

The motivating question is:

> Can overlapping deletion patterns create more digest states than plain subset selection?

If yes, that would be a genuinely new direction after `frontier-2`, because it would escape the flat local-choice upper bound without needing hash-path composition.

## Result 1: overlap-coded `FindAndDelete` is real in toy constructions

The new tool `tools/fad_overlap_search.py` does a toy exhaustive search over short payloads:

- payload alphabet `{01, 02}`
- payload lengths `1` and `2`
- `4` selectable payloads
- a script formed by concatenating each pushed payload once
- witness chooses an ordered `2`-of-`4`

Best toy example found:

- payloads: `01`, `02`, `0101`, `0201`
- script order: `02`, `0101`, `0201`, `01`
- script hex: `01020201010202010101`

Key numbers:

- ordinary unordered-subset baseline: `C(4,2) = 6`
- unique ordered post-deletion scripts found: `11`
- one unordered witness subset already has `2` different outcomes depending on order

Concrete order-sensitive subset:

- witness subset `{01, 02}`
- order `(01, 02)` gives outcome `02020201`
- order `(02, 01)` gives outcome `02010201`

So the first important point is:

**overlap-coded `FindAndDelete` is not imaginary. In raw byte space, it can create order-sensitive extra states beyond plain subset selection.**

## Result 2: the actual QSB minimal 9-byte dummy-signature surface does not expose that extra power

The same tool then probes actual QSB-style dummy signatures.

### Full round-1 pair probe on Config A

Using real QSB minimal 9-byte dummy signatures in a real Config A round-1 script:

- ordered pair queries: `22350`
- unique post-deletion scriptCodes: `11175`
- exact subset target: `C(150,2) = 11175`
- multiplicity: `2`

So for the full `n=150` actual surface, ordered pairs collapse exactly to unordered subsets.

### Ordered triple probes on actual QSB-style dummy signatures

For baseline-style round scripts:

- `n=20`
  - ordered triples: `6840`
  - unique post-deletion scriptCodes: `1140`
  - exact subset target: `C(20,3) = 1140`
  - multiplicity: `6 = 3!`
- `n=50`
  - ordered triples: `117600`
  - unique post-deletion scriptCodes: `19600`
  - exact subset target: `C(50,3) = 19600`
  - multiplicity: `6 = 3!`

That is exactly the same collapse pattern seen in `frontier-2`.

So the second important point is:

**the current QSB minimal dummy-signature surface behaves like pure subset deletion even under ordered queries.**

The overlap-coded behavior exists in theory, but not on the actual 9-byte surface QSB is using.

## Result 3: this closes a specific escape hatch and opens a narrower new one

This result matters because it separates two claims:

1. "FindAndDelete is just subset deletion in principle."
2. "FindAndDelete can be more expressive in principle, but the current QSB token family does not realize that expressivity."

The data supports claim 2.

That is stronger than both extremes:

- stronger than saying overlap-coded deletion is impossible,
- stronger than saying current QSB already exploits all of `FindAndDelete`.

What we now know is:

- the flat HORS family is saturated,
- grouped-choice loses,
- permutation is fake entropy on the current QSB surface,
- but `FindAndDelete` itself still has a more expressive regime in toy models.

## Result 4: the next frontier is no longer "better HORS" but "engineered overlap surfaces"

This is the real takeaway.

If there is another no-softfork direction left, it likely looks like this:

- intentionally engineered selectable patterns,
- designed so deletions interact,
- while still fitting inside Bitcoin Script and whatever validity constraints the selectable blobs must satisfy.

That is a much narrower and more concrete target than before.

It is also immediately clear why this is hard:

- QSB’s current minimal 9-byte signatures appear too rigid and too regular,
- any richer overlap surface likely needs longer or more structured selectable blobs,
- and longer blobs directly eat the already saturated byte budget.

So the next question is no longer abstract:

> Can an engineered overlap-coded selectable-token family create enough additional digest states per static byte to beat the current HORS frontier?

That is now the next meaningful research step in this repo.
