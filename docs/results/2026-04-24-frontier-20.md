# Frontier-20

Date: 2026-04-24

This report follows `frontier-19`.

`frontier-19` found the rescue gadget:

```text
OP_ROLL selected polyglot element
OP_DUP selected element
HASH160(preimage) == selected element
leave the duplicate as a CHECKMULTISIG dummy signature
```

That proved each round can be stack-correct in isolation.

This step checks the next failure mode:

> does the construction still work when pinning, round 1, and round 2 execute
> as one script against one shared stack?

That matters because round 1 leaves unselected hardcoded pool elements and a
`CHECKMULTISIG` truth value on the stack. If round 2's constants only worked in
an isolated round, the whole result would be a false positive.

## What changed

`tools/stack_correct_polyglot_frontier.py` now has a full symbolic script
builder:

- builds one witness stack for pinning, round 1, and round 2;
- executes the pinning puzzle first;
- executes round 1;
- executes round 2 on the resulting dirty stack;
- captures the exact emitted script bytes;
- compares the shallow-index and last-index witness paths;
- reports whether the full script fits the `10,000` byte and `201` non-push
  opcode limits.

This is still not a Bitcoin Core regtest spend. It does not prove DER parsing,
sighash handling, ECDSA, or policy relay. It proves the script stack accounting
that killed the earlier naive model in `frontier-17`.

The important part is not only that the default witness works.

The important part is:

- shallow-index and last-index witnesses emit the same script;
- round 2 survives the dirty stack left by round 1;
- the `143`, `198`, and `224` points still fit the consensus byte/op envelope.

## Result 2: the round-composed model was slightly optimistic, but not fatal

For the `143` Config-A crossing, full script accounting matches the
round-composed accounting exactly:

- `6389` bytes;
- `196` non-push opcodes.

For the two later points, full script accounting adds only stack-depth constant
bytes:

- `198` point: `+34` bytes;
- `224` point: `+23` bytes;
- no opcode increase.

This happens because the second round is not executing on a clean isolated
round stack. Its `OP_ROLL` constants sometimes need a larger push encoding.

That is precisely why this gate was needed. The hidden cost exists, but it is
small enough that the result survives.

## Result 3: cleanstack is the honest blocker

All three points end with the final `CHECKMULTISIG` result on top, but with many
unused hardcoded pool items below it:

- `143` point: final stack depth `395`;
- `198` point: final stack depth `271`;
- `224` point: final stack depth `235`.

So the current construction is validated under top-stack truth semantics, not
under a depth-one cleanstack requirement.

This is not a surprise. The MVP baseline already assumes a non-standard
transaction and miner-direct submission. But it is now explicit:

- if the target is consensus-level feasibility, the branch remains alive;
- if the target is standard relay / cleanstack compatibility, this branch is
  probably not the right path without a much deeper redesign.

Cleaning hundreds of leftover elements with `OP_DROP` is not viable under the
`201` opcode budget.

## Go/no-go

Decision:

**GO for the consensus-level / miner-direct research path.**

**NO-GO for claiming standard relay compatibility.**

The discovery is more robust than it was in `frontier-19`:

- the cheap `OP_ROLL + OP_DUP` gadget still works;
- the full pinning + two-round stack executes symbolically;
- the stronger `224` point remains comfortably under script and opcode limits;
- the only newly exposed blocker is cleanstack, which is outside the stated
  non-standard baseline but must be called out clearly.

## Next gate

The next step should not be more combinatorial search.

The next step is an external interpreter gate:

1. emit the full script bytes and witness stack for `strong_practical_224`;
2. run it through a Bitcoin Script interpreter under consensus-like flags;
3. run the same script under cleanstack / standardness flags and record the
   expected failure;
4. only after that, decide whether this is worth showing to Avihu as a real
   follow-up candidate.

## Bottom line

The full-stack accounting did not kill the result.

It narrowed the claim:

**this is now a plausible non-standard, miner-direct, consensus-envelope
candidate, not a standard-wallet transaction candidate.**
