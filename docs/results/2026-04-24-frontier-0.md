# Frontier-0

Date: 2026-04-24

## Question

What is the first thing worth learning beyond "QSB can work"?

Answer:

Whether the current HORS-like QSB construction is structurally near-optimal under Bitcoin’s legacy Script limits, or whether a limited-use variant can materially improve the frontier.

## Result 1: swapping in a modern hash function is not the frontier

This is the first place many people look, and it is probably the wrong place.

Bitcoin Script today exposes:

- `SHA256`
- `HASH256`
- `RIPEMD160`
- `HASH160`

It does not expose:

- SHAKE
- KangarooTwelve
- BLAKE3
- modern XOF-based domain separation machinery

That means a no-softfork design cannot win primarily by choosing a better on-chain hash primitive. Modern hash research still matters, but it matters in how we structure the digest/signature layer and how we tune limited-use assumptions.

## Result 2: direct SLH-DSA / FORS-style thinking is useful, but a direct port is probably wrong

Recent NIST work is relevant because it confirms the direction:

- [FIPS 205](https://csrc.nist.gov/pubs/fips/205/final) standardized SLH-DSA.
- [SP 800-230 IPD](https://csrc.nist.gov/pubs/sp/800/230/ipd), published on April 13, 2026, explicitly explores limited-signature parameter sets that trade generality for smaller signatures and faster verification.

That is conceptually aligned with Bitcoin UTXOs, which are naturally limited-use.

But a direct Bitcoin Script port of FORS / SLH-DSA-style authentication trees is likely to lose for a simpler reason: verification geometry.

Every authentication path introduces:

- more pushed data
- more on-chain hash checks
- more script structure overhead

Under a `10,000` byte script limit and a `201` non-push opcode budget, those costs likely dominate any elegance gained from moving toward a more standard tree-based design.

So the first useful negative result is:

"Modern limited-use hash-based signatures are the right conceptual inspiration, but naive tree-authentication ports are probably not the right Bitcoin realization."

## Result 3: the real optimization target is bits per opening and bits per opcode

The promising place to compete is not the hash primitive. It is the digest geometry.

The core questions become:

- How many effective digest bits do we get per revealed opening?
- How many effective digest bits do we get per non-push opcode?
- How tightly can the search space be tuned to the fixed hash-to-signature puzzle target?

This reframes the frontier:

- HORS-like QSB is good because it turns each verified opening into a lot of combinatorial entropy.
- Any improvement must either:
  - get more entropy per checked opening, or
  - keep similar entropy while cutting bytes/opcodes, or
  - reduce slack so search effort is not wasted against the fixed puzzle target.

## Result 4: the first backend worth building is a grouped-choice codebook

The first candidate that looks worth implementation is not "FORS in Bitcoin."

It is:

"A grouped-choice limited-use codebook construction with flat verification geometry."

The design goal is:

- keep verification local and repetitive
- avoid Merkle authentication paths
- tune search space precisely by changing group counts and group sizes
- preserve limited-use semantics

Why this is promising:

- it is closer to Bitcoin’s actual script constraints
- it can absorb lessons from modern limited-use signature research without inheriting tree overhead
- it gives the optimizer something concrete to search

## Result 5: a first concrete candidate already fits the target shape

The public QSB construction is tuned around a per-round search target of roughly `2^46`.

A grouped-choice construction can hit a very similar target cleanly:

- `15` groups with `8` choices each gives `8^15 = 2^45`
- `16` groups with `8` choices each gives `8^16 = 2^48`

That means a flat one-of-`8` grouped-choice round is already in the right neighborhood with only a small amount of tuning slack.

Why this matters:

- the candidate is simple enough to model immediately
- it avoids binomial subset-selection machinery
- it suggests that the real question is whether grouped-choice verification can be made byte- and opcode-efficient enough to beat the HORS-like baseline

This is not yet proof that grouped-choice wins. It is proof that it is a serious candidate, not a vague idea.

## Result 6: the first model run gives a real baseline to beat

Running `python3 tools/frontier_model.py` on the current v0 model yields:

- HORS-style baseline with two `k=9` rounds over `n=150`
  - raw choice entropy: `92.47` bits
  - tuning slack: `0.33` bits total versus the per-round `~2^46.4` target
- grouped-choice candidate with `15` groups of `8`
  - raw choice entropy: `45.00` bits
  - tuning slack: `1.40` bits versus the `~2^46.4` target

Interpretation:

- grouped-choice is close enough to the puzzle target to deserve real work
- the current HORS-style shape is still the tighter entropy match in the raw model
- therefore the grouped-choice family only wins if it buys enough byte or opcode savings to compensate

That is a real first frontier result:

"Grouped-choice is viable, but it does not obviously dominate. It needs a structural efficiency win, not just a similar search-space size."

## Current recommendation

The next engineering step should be:

1. encode the public HORS-like QSB point as the baseline
2. encode a grouped-choice codebook family as the first competitor
3. compare them on:
   - digest bits
   - bytes
   - non-push opcodes
   - search-space tuning slack
   - estimated honest work

If grouped-choice cannot win even in the model, that is already a strong result.
