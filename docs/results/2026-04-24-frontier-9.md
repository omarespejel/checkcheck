# Frontier-9

Date: 2026-04-24

This report follows `frontier-8`.

`frontier-8` introduced a new mechanized distinction:

- overlap-bearing families can still be subset-like,
- what mattered in the toy example was not overlap alone, but a fresh-occurrence cascade.

That looked promising, but it still left one serious open question:

> is cascade-bearing actually necessary for `FindAndDelete` expressivity, or is there a broader mechanism?

The new tool for this step is `tools/fad_mechanism_frontier.py`.

It classifies two mechanisms:

1. **fresh-occurrence cascade**
   a deletion creates a new later-match occurrence of a different live token;
2. **destructive conflict**
   a deletion destroys an already-existing occurrence of a different live token.

## Result 1: cascade is not necessary

The first important correction is that `frontier-8` did not identify the full invariant.

In the exhaustively searched `ternary_len2` toy universe, there are expressive orders with:

- no cascade witness,
- but a real destructive-conflict witness.

Representative conflict-only order:

- `0101`, `0102`, `0303`, `0203`

Its stats:

- expressive: yes
- unique ordered outcomes: `7`
- unordered subset baseline: `6`
- max unordered-subset multiplicity: `2`
- cascade witness: none
- destructive-conflict witness: yes

Representative conflict witness:

- selection order: `[0, 1]`
- after deleting token `1`, an already-existing occurrence of token `3` is destroyed
- destroyed occurrence provenance indices: `[5, 6, 7]`

So the repo has now falsified the stronger conjecture:

**cascade-bearing is not necessary for expressivity.**

## Result 2: destructive conflict looks like the better invariant

The tool then exhaustively classifies ordered families in several toy universes.

### `binary_len2_orders`

- total ordered families: `24`
- expressive orders: `23`
- expressive with conflict only: `0`
- expressive with cascade and conflict: `23`
- expressive with cascade only: `0`
- expressive without either mechanism: `0`

### `binary_len3_orders`

- total ordered families: `1680`
- expressive orders: `0`

### `binary_len4_orders`

- total ordered families: `43680`
- expressive orders: `0`

### `ternary_len2_orders`

- total ordered families: `3024`
- expressive orders: `1098`
- expressive with conflict only: `168`
- expressive with cascade and conflict: `930`
- expressive with cascade only: `0`
- expressive without either mechanism: `0`

This is the strongest mechanism result in the repo so far.

Across all of these exhaustively searched toy orders:

- every expressive order had a destructive-conflict witness,
- some expressive orders also had a cascade witness,
- no expressive order had cascade only,
- no expressive order had neither mechanism.

So the better working invariant is:

**expressivity seems to require destructive conflict; cascade is one important subclass, not the whole story.**

## Result 3: overlap-bearing exact-13 DER is conflict-free too

The tool then checks the explicit overlap-bearing exact-`13` DER pool from `frontier-7`.

### Exact-13 overlap pool, ordered `2`-of-`4`

- conflict found: `false`

### Exact-13 overlap pool, ordered `3`-of-`5`

- conflict found: `false`

So exact-`13` DER is now missing both mechanisms:

- no fresh-occurrence cascade from `frontier-8`,
- no destructive conflict from `frontier-9`.

That is a much cleaner explanation for why even overlap-bearing exact-`13` DER stayed subset-like.

## Result 4: random exact DER families also showed no destructive conflict

The tool runs random conflict search over exact DER surfaces:

- exact `13`, `m=4`, `t=2`, `2000` trials
- exact `14`, `m=4`, `t=2`, `2000` trials
- exact `15`, `m=4`, `t=2`, `1500` trials
- exact `13`, `m=5`, `t=3`, `1000` trials

Result in every case:

- `conflict_found: false`

So the current DER story is now sharper than before:

- overlap-bearing exact DER exists,
- but the searched DER families do not show cascade,
- and they also do not show destructive conflict.

That is why they keep collapsing to subset behavior.

## Result 5: this changes what the repo should optimize next

The cumulative picture is now:

- short DER below `13` fails partly because overlap is too limited,
- exact `13` can have real overlaps,
- but overlap alone is not enough,
- expressive toy families are conflict-bearing,
- the searched DER families are not.

That shifts the optimization target again.

The repo should no longer ask:

> can I make DER overlap more visible?

It should now ask:

> can I find a valid selectable blob family with real destructive conflict structure?

And if the answer keeps looking like no, then `FindAndDelete`-based overlap probably stops being the right frontier altogether.

## What is left

The next worthwhile moves are:

1. search for valid blob families that are explicitly **conflict-bearing**, not just overlap-bearing;
2. formalize a claim like:
   conflict-free and cascade-free families collapse to subset behavior;
3. if valid conflict-bearing families look implausible, move the repo away from `FindAndDelete` overlap and toward a different verification surface.

That is where the repo should go next.
