# Frontier-2

Date: 2026-04-24

This report extends `frontier-1` with three concrete checks:

1. an exact sweep of the HORS-like family under the current Bitcoin limits,
2. an explicit test of the ordered-selection / permutation loophole,
3. a sharper statement of the flat local-choice upper bound.

## Result 1: the public baseline is already the exact signed-digest optimum inside the HORS family

The updated model in `tools/frontier_model.py` swept `2,720,483` feasible HORS-family configurations under:

- script bytes `<= 10,000`
- non-push ops `<= 201`
- exact byte accounting validated against the imported upstream builder

The exact byte model was validated on the public upstream configs:

- `baseline_8_8`: measured `9953`, exact `9953`
- `configA_8p1b_7p2b`: measured `9967`, exact `9967`
- `alt_8p1b_8`: measured `9966`, exact `9966`

Best signed-digest point found:

- `n=150`
- round 1: `8+0b`
- round 2: `8+0b`
- `9953` bytes
- `197` ops
- `84.51` signed digest bits

That is exactly the public baseline.

So inside the current HORS-like design space, the first strong positive result is:

**there is no better signed-digest point than the public `150,8,8` baseline under today’s Bitcoin limits.**

## Result 2: bonus-heavy configs can maximize raw search space, but only by collapsing the signed digest

If the objective is only raw `FindAndDelete` subset count, the model finds pathological all-bonus points such as:

- `n=149`
- round 1: `0+18b`
- round 2: `0+18b`
- `9963` bytes
- `201` ops
- `151.79` subset-search bits
- `0.00` signed digest bits

This is useful because it exposes a modeling trap:

**raw subset-search bits are not a valid standalone optimization objective.**

They can be increased dramatically by spending all the budget on unsiged bonus selections, but that destroys the signed digest entirely.

So any serious objective has to keep both:

- signed digest bits
- search-space tuning / subset-search bits

in the loop.

## Result 3: Config A is the exact best practical search-space point once you require about 80 signed bits

The sweep also produced a practical tradeoff ladder:

- `signed >= 80`
  - `n=150`, `7+2b` and `8+1b`
  - `9967` bytes, `201` ops
  - `80.35` signed bits
  - `92.47` subset bits
- `signed >= 75`
  - `n=150`, `7+2b` and `7+3b`
  - `9968` bytes, `200` ops
  - `76.20` signed bits
  - `96.29` subset bits
- `signed >= 70`
  - `n=150`, `6+4b` and `7+3b`
  - `9969` bytes, `199` ops
  - `71.83` signed bits
  - `100.11` subset bits

This is the key interpretation:

- bonus slots do buy more search-space bits
- but they buy them by selling signed digest bits
- once you insist on staying around the public security level, the public Config A point is already the exact best tradeoff

So the second strong result is:

**if you want around 80 signed bits, the public Config A is already the exact optimum inside the current HORS-like family.**

## Result 4: the ordered-selection loophole is fake entropy

The natural hope after `frontier-1` was:

"Maybe ordered witness selections carry extra entropy, giving something closer to `P(n, t)` than `C(n, t)`."

The explicit probe says no, at least for the searched object that matters.

Exhaustive small-`n` results:

- `n=6`, `t=3`
  - ordered tuples: `120`
  - unique round scriptCodes: `20`
  - multiplicity per unique scriptCode: `6 = 3!`
- `n=7`, `t=3`
  - ordered tuples: `210`
  - unique round scriptCodes: `35`
  - multiplicity per unique scriptCode: `6 = 3!`

This means:

- permutations do exist syntactically
- but they collapse onto the same `FindAndDelete` result
- each unique subset gives one unique searched scriptCode, with `t!` redundant orderings

So the permutation factor is not real search entropy for QSB’s digest search.

That closes the easiest remaining loophole.

## Result 5: subset selection is not just better than grouped-choice; it is the extremal flat local-choice shape here

For the public round parameters:

- HORS round: `log2 C(150, 8) = 42.26`
- grouped-choice with the same `150` hardcoded options and `8` reveals:
  - `8 * log2(150 / 8) = 33.83`
- exact gap: `8.43` bits

For the `7`-signed round:

- exact gap: `7.15` bits

These match the asymptotic gap:

`log2 C(M, r) - r log2(M / r) ≈ r log2(e) - 0.5 log2(2πr)`

Interpretation:

- if the scheme is flat,
- if it uses local reveals,
- if it does not compose hash paths or aggregate many logical choices inside one reveal,

then subset selection is the extremal efficient shape.

That explains all of the empirical results so far:

- grouped-choice loses
- order does not rescue it
- tree-style schemes need composition support Bitcoin Script does not have
- public QSB points look close to the true frontier because they are already exploiting the right flat geometry

## Bottom line

After `frontier-2`, the next interesting result is no longer "find a better grouped-choice variant" or "tune HORS parameters harder."

Those avenues are mostly closed:

1. the public baseline is already the exact signed-digest optimum in the HORS family,
2. the public Config A is already the exact practical search-space optimum around `80` signed bits,
3. order does not create hidden free entropy,
4. grouped-choice is structurally dominated,
5. tree-style ports need a verification surface Bitcoin does not currently expose.

So the next frontier has to come from a different place:

- compressing many logical choices into one checked opening,
- or changing the verification surface,
- or exploiting a Script quirk that is more powerful than flat local selection.
